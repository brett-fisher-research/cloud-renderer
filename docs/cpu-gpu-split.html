Anatomy of a cloud frame

Where the work actually happens, measured at 1280×720 on a Radeon RX 7800 XT. The short version: the CPU is a courier, and one shader does everything.

Per frame, 60 times a second

Rust never touches a pixel. It updates 80 bytes, records three commands, hands them over, and then waits. Everything below the dashed line is the GPU running clouds.wgsl.

The 16.7 ms budget

GPU · 7.6 ms
waiting for vsync · 9.1 ms
CPU < 0.1 ms fragment shader idle

At vsync the renderer has roughly 2× headroom. That slack is the budget for the roadmap: more march steps, a second noise layer, or a higher resolution.

Why the fragment shader dominates

Three vertices become nearly a million pixels, and each one marches the cloud layer independently. The fan-out is the whole story.

Vertices 3 one full-screen triangle
Fragments 921,600 1280 × 720
Per pixel 448 density lookups, worst case
Per lookup 5 octaves of value noise

The 448 comes from the two nested marches: 64 steps along the view ray, and at each step that lands inside cloud, 6 more steps toward the sun to find the shadow. Clear-sky samples skip the sun march entirely, and the loop stops once transmittance falls below 0.01, so the real average is well under the worst case.

This is why --release changes nothing here. Rust’s optimiser never sees the shader — Mesa compiles that to GPU machine code at pipeline creation, identically in both builds. Measured: 7.74 ms debug, 7.75 ms release.

Startup, and every time you save

The shader is read from disk at runtime, not baked into the binary. That is what makes hot-reload possible, and it is also the only moment any WGSL compilation happens.
